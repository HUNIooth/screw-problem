# Problem Discovery

목표: **사용자가 현재 상태, 중요한 선택, 다음 지시와 결과 확인 방법을 이해하고, 다른 에이전트는 문서만으로 작업을 이어갈 수 있게** 만든다.

**사람이 보는 문서는 `사용자_검토.md` 한 장이다.** REQUIREMENTS, PLAN, AGENTS, HANDOFF는 AI용이라 사람이 열어 볼 필요가 없게 쓴다. 사람이 알아야 하거나 정해야 하는 것은 반드시 `사용자_검토.md`에 있어야 한다. 방향타는 사람이 실제로 볼 때만 작동한다.

모호한 문제에서 가장 비싼 실수는 잘못된 문제를 푸는 것이다. 문서를 원했는데 앱을 만들거나, 원본이 아닌 사본으로 작업하는 식이다. 실행 전에 조금 더 찾고 묻는 편이 다시 만드는 것보다 싸다.

이 스킬의 범위는 계획과 인계다. 현재 요청이 문서 작성까지라면 구현을 시작하지 않는다. 사용자가 이미 실행까지 요청했다면 같은 허락을 다시 묻지 않고 HANDOFF.md와 생성된 AGENTS.md를 따라 진행하되, **준비 판정이 🟢이거나 🟡의 남은 추정을 사용자가 승인했을 때만** 진행한다. 🔴이면 실행 요청이 있어도 멈추고 무엇이 부족한지 알린다.

### drill-pilot에서 이어받을 때

- 기존 `사용자_검토.md`와 대화에서 역할, 결정권, 이해의 근거, 남은 질문을 먼저 읽고 이미 받은 답은 다시 묻지 않는다. 사용자 원문과 담당자 발언은 보존한다.
- drill-pilot의 최소 10턴과 이 스킬의 질문 라운드 제한은 별개다. 여기서 10턴을 새로 시작하지 않는다.
- drill-pilot은 필수 선행 스킬이 아니다. 직접 계획을 요청한 사용자에게 긴 인터뷰를 강제하지 않는다.

## 시작 전: 설정 확인

- `~/.screw-problem/설정.md`를 읽는다. 없으면 `$screw-setup`을 먼저 하자고 한 줄로 제안한다. 건너뛰면 권한이 걸린 것(멀티에이전트, 설치/푸시/외부 전송)은 허용하지 않은 것으로 두고 필요한 순간에 묻는다. 건너뛴 것은 허락이 아니다. '설정 없음'을 `사용자_검토.md`에 적는다.
- 이번 과제의 `사용자_검토.md`에 '작업 설정'이 없으면 다른 질문보다 먼저 두 가지만 묻는다: 이 문제가 내 문제인지 현업 요건 구현인지(결정권자 포함), 이번에만 더해지는 제약. 설정의 평소 역할을 기본값으로 보여 주고 "그대로"면 넘어간다. drill-pilot이 이미 적어 두었으면 묻지 않는다.
- 설정의 사용 경험(처음이면 할 일을 한 줄씩 덧붙임), 공통 제약, 멀티에이전트 허용을 따른다.

## 0. 규모 정하기

시작할 때 한 줄로 알리고 진행한다.

- **경량**: 반나절 안쪽, 산출물 하나, 결정권자 한 명. `HANDOFF.md` 하나에 요구사항, 계획, 사용자 판단과 피드백 안내를 넣는다. 경량이라도 수행 에이전트는 **끝내기 전에 한 번 멈춰** 한 일, 볼 것, 놓쳤을 수 있는 것을 올리고, 커밋은 사용자 컨펌 뒤에 한다. 기존 사용자 검토 문서가 있다면 보존하고 연결한다.
- **표준**: 그보다 크거나 여러 에이전트가 나눠 맡을 일. 기존 인계 문서 4종과 `사용자_검토.md`를 쓴다.

## 1. 먼저 찾기

사용자에게 묻기 전에 직접 찾는다. 사용자에게 물을 것은 **사용자만 아는 것(의도, 결정, 선호)** 이고, 사실 확인은 내 몫이다.

- 볼 곳: 작업 폴더의 기존 파일, `AGENTS.md`, README, 작업 기록, 설계 문서, 원천 자료(업무 규정 문서, 데이터 샘플, 이전 산출물), 필요하면 웹.
- 폴더가 크고 하위 에이전트를 쓸 수 있으면 "무엇이 어디 있는지"만 맡기고 결론만 받는다.
- 결과를 **지식 장부** 표로 정리해 대화에 보여 준다.

| 구분 | 내용 | 근거 | 영향 |
|---|---|---|---|
| 사실 | 확인된 것 | 파일:줄, URL, 사용자 발언 | - |
| 모름 | 아직 모르는 것 | - | 높음/중간/낮음 |
| 추정 | 그럴 것 같지만 확인 안 된 것 | 추정 이유 | 높음/중간/낮음 |

근거를 댈 수 없으면 사실 칸에 넣지 않는다. 추정을 사실처럼 적는 것이 이 단계에서 가장 흔하고 해로운 실수다.

## 2. 빈틈 순위

'모름'과 '추정' 항목마다 두 가지를 본다.

- **영향**: 틀리면 결과물이 뒤집힌다(높음), 일부 고친다(중간), 사소하다(낮음)
- **푸는 방법**: 조사하면 풀림, 사용자만 앎, 해 봐야 앎

처리:
- 조사로 풀리는 것: 묻지 말고 조사한다.
- 사용자만 알고 영향이 높은 것: 3단계 질문의 최우선.
- 사용자가 구현자라 업무 기준을 모르면 실제 결정권자에게 보낼 질문과 답 없이 진행할 작업을 분리한다. 기술적 선택과 회사의 업무 사실을 혼동하지 않는다.
- 해 봐야 아는 것: 계획의 첫 단계(시험 작업)로 보낸다.
- 영향이 낮은 것: 기본값을 정하고 '추정'으로 남긴다. 묻지 않는다.

아래 여섯 가지는 빠지면 반드시 구멍이 나므로 장부에 하나씩은 있어야 한다.

1. **목적과 성공 기준**: 왜 하나, 끝났다는 걸 무엇으로 아나
2. **산출물 형태**: 앱, 스크립트, 파이프라인, API 중 무엇이고 누가 어디서 돌리나. "만들어 줘"가 설계 문서 요청일 수도 있다.
3. **입력과 원천**: 자료가 어디 있고 믿을 만한가, 원본인가 사본인가
4. **제약**: 기한, 비용(토큰 포함), 보안, 권한, 금지 사항, 써야 하는 도구
5. **경계와 예외**: 범위 밖인 것, 예외 상황, 실패하면 어떻게 하나
6. **결정과 검토**: 누가 정하고 누가 검토하나, 결과물을 누가 받나

문제 유형별 추가 질문은 [references/question-bank.md](references/question-bank.md)에서 해당 유형만 골라 읽는다.

## 3. 질문하기

지금 답할 수 있는 질문(앞선 결정이 이미 정해진 것)만 한 라운드로 묶는다. 다른 질문의 답에 따라 달라지는 질문은 다음 라운드로 미룬다.

형식:

```
Q1. <질문 제목>
왜: <틀리면 무엇이 뒤집히는지 한 줄>
  A. <선택지>: <고르면 어떻게 되나>
  B. <선택지>: <고르면 어떻게 되나>
  C. <선택지>: <고르면 어떻게 되나>
  D. 직접 입력
추천: A (<이유>)
```

- **결정 질문은 선택지를 3개 이상** 주고 추천 이유와 함께 하나를 추천한다. 사용자가 "Q1 A, Q2 C"처럼 짧게 답할 수 있고, 생각 못 한 길도 보여 줄 수 있다.
- 선택지는 실제로 다른 결과를 내는 것만 넣는다. 진짜 선택지가 2개뿐이면 2개로 둔다. 개수를 채우려고 억지 선택지를 만들지 않는다.
- 항상 '직접 입력'을 둔다. 선택지 밖에 정답이 있을 수 있다.
- **사실 질문(날짜, 경로, 건수, 이름)은 선택지 없이** 열어서 묻고 답 예시를 단다. 사실을 선택지로 지어내면 그중 하나가 골라져 틀린 사실이 들어온다.
- 한 라운드 핵심 질문은 최대 3개, 영향 높은 것부터. 지금 답할 수 없는 후속 질문은 미룬다.
- 질문을 보냈으면 **턴을 끝내고 답을 기다린다.** 답을 받지 않은 채 추천 답으로 계속 진행하지 않는다.
- 사용자가 "알아서 해"라고 하면 추천 답을 채택하고 '추정(사용자 위임)'으로 기록한다.
- 비대화 실행(`codex exec` 등)이라 물을 수 없으면 추천 답을 모두 '추정'으로 기록하고 준비 판정을 🟡 이하로 둔다.
- 라운드가 끝나면 장부를 갱신하고, 새로 열린 질문만 다음 라운드로 보낸다.
- 세 라운드 이후에는 새로운 세부 질문을 늘리기 전에 계획 전환을 제안한다. 남은 고영향 항목은 확인 또는 시험 단계로 표시한다. 침묵을 승인으로 해석하지 않는다.
- 사용자 역질문에는 먼저 설명한다. 개념 설명으로 풀리는 것, 현업 확인이 필요한 것, 시험해야 아는 것을 나눈다.

## 4. 요구사항으로 바꾸기

- 항목마다 `R-01` 번호, 내용, **검증 방법**(통과를 어떻게 판정하나), 근거(장부 항목), 필수/희망.
- 검증할 수 없는 말은 바꾼다. "빠르게"는 "10초 안에"로, "깔끔하게"는 기준 문서나 예시 지정으로.
- **범위 밖**을 따로 적는다. 수행 에이전트가 선의로 일을 키우는 걸 막는 가장 싼 방법이다.

## 5. 대안과 계획

- 방법이 여럿이면 2~3개를 장단점, 위험, 비용으로 비교하고 하나를 추천한다. 사실상 하나뿐이면 생략.
- 마이너 작업마다 산출물, 통과 기준, 선행 작업을 적는다.
- 사용자가 다음 작업을 맡길 수 있도록 지시문, 받을 결과, 직접 볼 검증 증거, 실패 시 다음 행동을 구체화한다. 아직 실행하지 않은 명령이나 결과는 제안/미실행으로 표시한다.
- **메이저 기능과 마이너 작업으로 잘게 나눈다.** 메이저는 사용자가 얻는 기능 단위, 마이너는 한 가지 일이면서 테스트로 통과를 판정할 수 있는 크기다.
- **메이저 기능마다 커밋 분기점을 2개 이상** 정한다. 자리가 분명하면 내가 정하고, 층으로 나눌지 기능 흐름으로 나눌지처럼 갈리면 선택지와 추천을 붙여 사용자에게 묻는다.
- **확인 리듬**: 마이너 3개마다 묶음 확인, 커밋 분기점마다 검토, 설명, 이해 질문, 컨펌 뒤 커밋. 지침이나 README와 안 맞는 마이너 작업은 바로 묻는다. 수행 에이전트는 이 지점들에서 반드시 멈춘다. 사용자가 미리 생략을 지시한 범위만 예외로 하고, 그 지시는 원문으로 남긴다.
- 코드를 고치는 단계는 통과 기준을 테스트로 적는다. 테스트 먼저, 원인 확인 후 수정, 실행 증거 없이 완료 금지는 AGENTS.md 양식의 작업 규칙을 따른다.
- 영향 높은 '해 봐야 아는 것'은 맨 앞 시험 단계로 두고, 실패하면 계획을 다시 짜는 분기점도 적는다.
- 동시에 돌릴 수 있는 단계를 표시한다. 여러 에이전트로 나눌 때 쓴다.

## 6. 준비 판정

- [ ] 영향 높은 '모름'이 남아 있지 않다 (시험 단계로 보낸 것은 제외)
- [ ] 필수 요구사항마다 검증 방법이 있다
- [ ] 산출물 형태와 저장 위치가 정해졌다
- [ ] 완료 조건을 제3자가 판정할 수 있다
- [ ] 권한과 금지 사항이 적혀 있다
- [ ] 메이저 기능마다 커밋 분기점이 2개 이상이고, 분기점마다 볼 것과 계속/수정/중단 기준이 있다
- [ ] 마이너 작업마다 통과 기준(테스트)이 있다
- [ ] 사용자가 이번에 결정할 것과 다음 작업, 결과 확인 방법을 `사용자_검토.md` 한 장에서 볼 수 있다
- [ ] 사용자 이해의 확인 근거가 있거나, 아직 미확인임을 명시했다

판정:
- 🟢 **실행 가능**
- 🟡 **조건부**: 남은 추정 목록을 사용자가 승인하면 실행 가능
- 🔴 **추가 탐색 필요**: 무엇을 더 알아야 하는지 적고 1~3단계로 돌아간다. 사용자가 그래도 진행하겠다면 위험을 HANDOFF.md 맨 위에 적고 문서를 만든다.

## 7. 인계 문서

**위치**: 사용자가 지정한 산출물 폴더를 우선한다. 지정이 없으면 작업 폴더 아래 `discovery/<YYYYMMDD>_<주제>/`에 둔다. 기존 문서가 있으면 먼저 읽고 프로젝트의 판 관리 규칙을 따른다. 인계용 `AGENTS.md`로 작업 폴더 루트의 기존 지침을 덮어쓰지 않는다.

|---|---|---|
| 사용자_검토.md | 역할, 현재 이해, 정할 것, 다음 작업, 확인 지점, 피드백과 반영 결과 | **사람이 보는 유일한 문서** |
| REQUIREMENTS.md | 무엇을, 왜, 성공 기준, 범위 밖 | AI용, 합의된 내용 |
| PLAN.md | 메이저/마이너 분해, 커밋 분기점, 확인 리듬 | AI용, 방법 |
| AGENTS.md | 수행 에이전트의 역할, 권한, 금지, 입출력, 일하는 방식 | AI용, 잘 안 바뀜 |
| HANDOFF.md | 지금 상태, 다음 행동, 남은 추정, 읽는 순서 | AI용, 계속 바뀜 |

`사용자_검토.md`를 작성하거나 갱신할 때 [references/user-review.md](references/user-review.md)를 읽는다. 기존 네 문서의 전체 내용을 복제하지 말고 세부 근거로 연결한다. 사용자 직접 작성 영역은 원문을 보존한다.

### 피드백을 받았을 때

- 사용자 발언, 에이전트 해석, 확정된 결정을 구분한다. 중요한 해석이 갈리면 그 부분만 묻는다.
- 현재 허용 범위의 명확한 수정 지시는 반영한다. 문서 피드백을 구현이나 외부 작업 승인으로 확대하지 않는다.
- 목적/범위/성공 기준은 REQUIREMENTS, 방법/순서/검증은 PLAN, 지속적인 권한/규칙은 AGENTS, 진행 상태/다음 행동은 HANDOFF에 반영한다.
- 변경 전후, 이유, 실제 검증 결과와 남은 질문을 사용자 검토 문서에 요약한다. 영향 없는 문서는 불필요하게 다시 쓰지 않는다.
- 반영 직전에 사용자 문서를 다시 읽어 새 피드백을 덮어쓰지 않는다. 빈 답변은 동의가 아니다.
- 수행 에이전트는 스킬 없이 AGENTS.md만 보고 일한다. 그래서 생성하는 AGENTS.md에서 양식의 확인 리듬, 메이저 커밋, 놓쳤을 수 있는 것 묻기, 사용자 지식 녹이기, 작업 규칙, 검토를 빼지 않는다. [references/review/](references/review/)의 점검표 세 개는 인계 폴더의 `review/`로 복사한다.

쓰고 나서 **자기 완결 점검**: "이 대화를 못 본 에이전트가 HANDOFF.md부터 열어 첫 작업을 시작할 수 있나?"
- **사용자 점검**: "사용자가 사용자_검토.md만 보고 다음 지시와 결과 수용 여부를 판단할 수 있나?"
- 대화에서만 나온 용어, 약어, 별명은 정의를 붙이거나 풀어 쓴다.
- 경로는 절대경로로 쓴다.
- "앞에서 말한", "그 파일" 같은 대화 의존 표현을 없앤다.
- 사용자가 내린 결정은 이유와 함께 적는다. 이유가 없으면 수행 에이전트가 같은 질문을 다시 꺼낸다.

중요한 인계라면 하위 에이전트에게 HANDOFF.md 경로만 주고 "첫 작업과 모르는 점을 말하라"고 시험할 수 있다. 토큰이 드니 사용자가 원할 때만 한다.

문서는 개조식과 표로 쓰고 표지, 배지, 장식은 넣지 않는다. 같은 내용을 제목, 요약, 본문에서 되풀이하지 않는다.

## 8. 보고

대화에 짧게 남긴다.

- 만든 파일 경로
- 준비 판정(🟢/🟡/🔴)과 이유 한 줄
- 승인이 필요한 추정 상위 3개
- 다음 행동: 누가(사용자, 이 세션, 다른 에이전트) 무엇을. 새 세션에 넘길 때는 프로젝트 루트에서 열고 `<HANDOFF.md 절대경로> 읽고 시작해`를 붙여 넣으라고 안내한다. 인계 하위 폴더에서 열면 바깥 파일을 못 고칠 수 있다.
- 사람이 먼저 읽을 `사용자_검토.md` 또는 경량 문서의 해당 부분

마지막 줄은 상태줄(✅ 완료 / ⏳ 진행 중 / 🛑 결정 필요)로 끝낸다.

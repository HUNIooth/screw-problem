## AGENTS.md

수행 에이전트가 작업 내내 따르는 지침. 진행 상태는 여기 쓰지 않는다(HANDOFF.md에).

```markdown
# <주제> 수행 지침

## 역할
- 너는 <무엇을 하는> 에이전트다. 목표는 REQUIREMENTS.md의 필수 요구사항을 모두 통과시키는 것이다.

## 읽는 순서
1. HANDOFF.md (현재 상태와 다음 행동)
2. 사용자_검토.md (새 피드백과 사용자 판단)
3. REQUIREMENTS.md
4. PLAN.md

## 권한
- 읽어도 되는 곳: <절대경로>
- 써도 되는 곳: <절대경로>

## 금지
- <건드리면 안 되는 파일/원본>
- <호출하면 안 되는 서비스/과금 API>
- <사용자 확인 없이 하면 안 되는 일: 삭제, 외부 전송, 배포 등>

## 입력과 출력
| 구분 | 내용 | 위치 | 형식 |
|---|---|---|---|
| 입력 | | | |
| 출력 | | | |

## 일하는 방식

### 확인 리듬
PLAN은 메이저 기능(M1, M2...)과 그 안의 마이너 작업(M1.1, M1.2...)으로 나뉜다.
- **마이너 작업 3개를 끝낼 때마다** 멈추고 사용자_검토.md에 묶음 확인을 쓴다: 끝낸 작업, 볼 것(경로, 테스트 결과), 놓쳤을 수 있는 것. 사용자가 계속이라고 하기 전에는 다음 묶음으로 가지 않는다.
- **마이너 작업이 이 지침, README, 사용자 기준과 맞지 않으면** 3개를 기다리지 않고 바로 멈추고 묻는다: 어느 문장과 어떻게 어긋나는지, 선택지(지침대로 / 지침을 바꾼다 / 이번만 예외 / 직접 입력), 추천.
- **커밋 분기점에서는** 아래 '메이저 커밋'을 따른다. 커밋 분기점이 묶음 확인과 겹치면 커밋 확인 하나로 합치고, 커밋 확인 뒤에는 마이너 개수를 0부터 다시 센다.
- 이미 승인받은 범위는 새 쟁점이 생겼을 때만 다시 묻는다. 같은 결정을 표현만 바꿔 재확인하지 않는다.
- 사람에게 알릴 것은 사용자_검토.md에 쓴다. 비대화 실행이면 멈출 지점에서 실행을 끝낸다. 사용자가 미리 생략을 지시한 범위만 예외다.

### 메이저 커밋
메이저 기능은 PLAN의 커밋 분기점마다 커밋하고, 기능 하나에 **최소 2번** 커밋한다. 커밋은 사용자 컨펌 뒤에만 한다.
1. **검토**: 아래 '검토' 절차로 이번 변경분을 점검한다.
2. **설명**: 사용자_검토.md에 무엇을 어떻게 짰는지 쉬운 말로 쓴다. 어떤 파일이 무슨 일을 하는지, 데이터가 어디서 들어와 어디로 가는지, 내가 고른 설계와 그 결과.
3. **이해 질문**: 사용자가 알아야 할 설계 선택을 질문으로 묻는다. '놓쳤을 수 있는 것'과 합쳐 한 번에 최대 3개. "이렇게 짰고, 그래서 X 상황에서는 Y가 됩니다. 이대로 갈까요, 바꿀까요?" 지식 시험이 아니라 선택을 확인하는 질문이다.
4. **컨펌 후 커밋**: 사용자가 컨펌하면 커밋한다. 메시지에 메이저/분기점 번호와 R-번호를 넣는다. 수정 지시면 고치고 1부터 다시 한다.
- PLAN에 분기점이 없거나 작업하다 나누는 자리가 맞지 않게 되면 분기점을 역질문으로 정한다: 나눌 자리 선택지 3개, 추천, 이유.
- git 저장소가 아니면 처음 커밋 분기점에서 저장소를 만들지 묻는다.

### 사용자가 놓쳤을 수 있는 것 묻기
사용자는 이 문제를 처음 보는 사람일 수 있다. 사용자가 말하지 않았지만 결과를 바꾸는 것은 내가 먼저 짚는다.
- 언제: 묶음 확인과 커밋 확인마다. 그리고 요구사항에 없는 결정을 내려야 하는데 나중에 되돌리기 비싼 순간.
- 무엇을: 작업하며 실제로 발견한 것만. 데이터가 사용자 설명과 다름, 처리 규칙이 없는 예외, 입력 형식이 바뀔 가능성, 개인정보와 권한, 사람이 확인해야 할 지점, 운영 중 누가 고치나, 비용, 모호한 검증 기준.
- 몇 개: 한 번의 멈춤에서 사용자에게 가는 질문은 이해 질문까지 합쳐 **최대 3개**, 영향 큰 것부터. 넘치면 HANDOFF.md '열린 질문'에 두고 다음 멈춤에 꺼낸다. 없으면 "없음".
- 형식: 질문, 왜(놓치면 생기는 일), 답이 없을 때의 기본값. **결정 질문**(어느 쪽으로 할까)은 선택지 3개 이상과 직접 입력, 추천을 붙인다. **사실 질문**(실제로 어떤 값, 사례, 규칙이 있나)은 선택지 없이 열어서 묻고 답 예시만 단다. 사실을 선택지로 지어내면 그중 하나가 골라져 틀린 사실이 들어온다.
- 영향이 큰 질문은 답을 받기 전에 그 부분을 진행하지 않는다. 작은 것은 기본값으로 진행하고 HANDOFF.md '남은 추정'에 적는다.
- 조사로 알 수 있는 것, 이미 답한 것은 묻지 않는다. 지식 시험처럼 묻지 않는다.

### 사용자 지식 녹이기
- 사용자의 답, 수정 지시, 피드백 중 다음 단계에도 적용될 것은 아래 '사용자 기준' 표에 원문과 함께 규칙으로 추가하고, 사용자_검토.md에 "규칙으로 남긴 것"으로 알린다. 이후 모든 단계는 이 표를 따른다.
- 목적/범위/성공 기준이 바뀌면 REQUIREMENTS, 방법/순서가 바뀌면 PLAN, 진행 상태는 HANDOFF에 반영한다. 영향 없는 문서는 다시 쓰지 않는다.
- 사용자 원문, 담당자 발언, 내 해석을 구분한다. 사용자가 직접 쓴 칸은 고치지 않는다. 갱신 직전에 파일을 다시 읽는다.
- 빈 피드백은 동의가 아니다. 이미 받은 허락은 다시 묻지 않는다. 피드백은 확인 지점이나 사용자가 반영을 요청할 때 읽는다.

### 범위
- 요구사항에 없는 기능을 더하지 않는다. 필요해 보이면 '놓쳤을 수 있는 것'으로 묻는다.
- 기술 검증 통과와 실제 업무 사용자의 수용을 따로 기록한다.

### 작업 규칙
코드를 고치는 작업:
- **테스트 먼저**: 마이너 작업마다 실패하는 테스트를 먼저 쓰고 실제로 실패하는 것을 본다. 통과할 만큼만 구현하고, 통과를 확인한 뒤 정리한다.
- **버그는 원인부터**: 재현하고, 가설을 하나씩 확인한다. 원인을 확인하기 전에는 고치지 않는다. 같은 문제에서 수정이 두 번 실패하면 멈추고 사용자에게 올린다.
- **증거 없이 "됐다"고 하지 않는다**: 테스트와 실행 명령을 실제로 돌리고 결과 일부를 사용자_검토.md에 붙인다. 돌리지 않은 것은 '미실행'.
- **마이너 작업은 작게**: 한 가지 일, 테스트로 통과를 판정할 수 있는 크기.

코드가 아닌 작업(문서, 분석, 데이터 정리)도 같다. 통과 기준을 먼저 정하고, 결과를 기준에 대조한 증거를 붙인다.

### 검토
점검표는 이 파일을 짧게 두려고 따로 있다: `review/clean-code.md`, `review/architecture.md`, `review/security.md`.
- **마이너 작업마다**: 아래 다섯 줄만 스스로 확인한다.
  - 함수 하나는 한 가지 일, 이름만 봐도 하는 일을 안다.
  - 입출력(화면, API), 업무 규칙, 저장(CRUD)을 한 함수나 파일에 섞지 않는다.
  - 의존은 바깥(화면, DB, 외부 API)에서 업무 규칙 쪽으로만 향한다.
  - 비밀값을 코드에 쓰지 않고, 외부 입력은 검증하고, 쿼리는 매개변수로 넘긴다.
  - 같은 코드를 세 군데 복사하지 않는다.
- **커밋 분기점마다**: `review/` 세 파일로 변경분(diff)을 점검한다. 보안 치명 항목이 걸리면 커밋하지 않는다. 못 고친 것은 이유와 함께 사용자_검토.md에 올린다.
- 프로젝트에 린터, 포매터, 보안 스캐너가 있으면 먼저 돌린다. 도구가 잡는 건 도구에 맡긴다.
- 검토는 짠 쪽이 스스로 한다. 선택: 변경이 크고 하위 에이전트를 쓸 수 있으면 diff와 점검표만 주고 맡겨도 된다.
```

# 구조 점검표 (클린 아키텍처, 스파게티 방지)

커밋 확인 때 이번 변경이 구조를 흐트러뜨리지 않았는지 본다.

## 네 겹으로 나눈다

| 층 | 하는 일 | 예 |
|---|---|---|
| 입출력 | 화면, API 엔드포인트, CLI, 파일 입출력 | 요청을 받아 처리 흐름에 넘기고 결과를 돌려준다 |
| 처리 흐름 | 한 가지 사용 장면을 순서대로 진행 | "신청 접수", "보고서 생성" |
| 업무 규칙 | 판단 기준, 계산, 검증 | "한도를 넘으면 반려" |
| 저장과 외부 연결 | DB, 외부 API, 메시지, 파일 저장소 | 저장소(repository), API 클라이언트 |

- **의존 방향은 바깥에서 안쪽으로만.** 입출력 → 처리 흐름 → 업무 규칙. 업무 규칙은 DB, 화면, 외부 API를 직접 부르지 않는다. 저장이 필요하면 처리 흐름이 저장소를 불러 결과를 넘긴다.
- **작은 프로젝트에 층을 억지로 만들지 않는다.** 파일 몇 개짜리면 함수 단위로 나누는 것으로 충분하다. 층을 나누는 이유는 바꿀 때 한 곳만 고치기 위해서다.

## CRUD 분리

| 점검 | 걸리는 신호 |
|---|---|
| 읽기와 쓰기 | 한 함수가 조회도 하고 수정도 하고 화면용 가공까지 함 |
| SQL과 쿼리 위치 | 화면 코드나 업무 규칙 안에 SQL/쿼리가 직접 있음 |
| 저장소 | 같은 테이블을 여러 파일이 제각각 직접 읽고 씀 |
| 반환 모양 | DB 행을 그대로 화면까지 넘김 (화면이 테이블 구조에 묶임) |

조회와 변경은 저장소의 별도 함수로 두고, 처리 흐름에서 조합한다.

## 스파게티 신호

- 두 모듈이 서로를 import한다 (순환 의존)
- 전역 변수나 싱글턴 상태를 여러 곳에서 고친다
- 한 파일이 400줄을 넘고 계속 커진다
- 같은 `if`/`switch` 분기가 여러 파일에 반복된다
- 설정값(경로, 키, URL)이 코드 곳곳에 박혀 있다
- 한 가지 기능을 고치려면 관련 없어 보이는 파일 여러 개를 함께 고쳐야 한다

걸리면 이번 커밋에서 고칠지, 다음 마이너 작업으로 미룰지를 사용자_검토.md에 올려 묻는다. 구조를 크게 바꾸는 리팩터링은 사용자 확인 없이 하지 않는다.

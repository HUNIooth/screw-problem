# 사용자 검토 안내 작성과 갱신

사용자가 현재 상태를 이해하고 다음 지시와 결과 수용 여부를 판단하도록 돕는다. 처음 작성할 때와 사용자 피드백을 반영할 때 읽는다.

## 작성 원칙

- 사람이 보는 문서는 이 한 장이다. 사람이 알거나 정해야 할 것은 모두 여기 있어야 하고, 세부는 AI용 문서(REQUIREMENTS, PLAN, AGENTS, HANDOFF)로 연결만 한다.
- 목적, 현재 상태, 다음 행동을 먼저 보여 준다. 기술 설명은 지금의 판단에 필요한 만큼만 하고 사례를 붙인다.
- 이번에 답할 수 있는 질문을 최대 3개만 보여 준다. 역할과 결정권이 미확인이면 먼저 확인하고, 그 답에 의존하는 업무 질문은 뒤로 미룬다.
- 질문마다 왜 필요한지, 누가 답할 수 있는지, 답이 무엇을 바꾸는지 적는다. 결정 질문에는 선택의 차이와 추천 이유를 붙인다. 업무 사실을 선택지로 지어내지 않는다.
- 사용자 역할, 이해 상태, 실제 인터뷰 완료 회차를 추정하지 않는다. 스킬을 설계한 대화와 실제 과제 인터뷰를 구분한다.
- 사용자 발언, 현업 발언, 자료로 확인한 사실, 에이전트의 제안을 구분한다.
- 합의된 기준과 상세 계획은 REQUIREMENTS/PLAN을 참조한다. 사용자 검토 문서는 전체 명세의 사본이 아니다.
- 사용자가 적은 피드백은 원문을 보존한다. 에이전트는 별도 영역에서 해석과 반영 내용을 작성한다.

## 6대 병목 점검

현재 작업에 해당하는 항목만 보고, 이 표 전체를 매번 사용자에게 출력하지 않는다.

| 병목 | 안내가 해 줘야 할 일 |
|---|---|
| 인지 | 목적, 사용하는 사람, 현재 상태, 다음 행동을 짧게 설명 |
| 입력 | 기존 자료와 답변을 재사용하고 부족한 정보만 요청 |
| 판단 | 사용자 결정, 담당자 확인, 에이전트 조사/시험을 구분 |
| 실행 | 선택을 구체적 지시로 바꾸고 허용 범위에서 수행. 막힌 원인과 대안 기록 |
| 검증 | 통과 기준과 실제 증거를 함께 제시. 미실행과 실패를 숨기지 않음 |
| 수용 | 실제 사용자나 검토자가 대표 업무에 적용해 본 반응과 남은 조정 사항 기록 |

## 사용자_검토.md 양식

```markdown
# <주제> 사용자 검토

- 갱신: <날짜>

## 작업 설정
- 이 문제는: 내 문제 / 현업 요건 구현 / 둘 다 — 결정권자: <이름 또는 미확인>
- 이번에 더해지는 제약: <공통 제약 외, 없으면 없음>
- 멀티에이전트: 설정대로(<값>) / 이번엔 다르게: <>
- 모델: 설정대로(<값>) / 이번엔 다르게: <>
- 이해 대화: <실제 완료 회차 또는 미착수/미확인>

## 현재 상태
- 목적:
- 완료한 것:
- 남은 것:
- 현재 이해와 근거: <사용자 설명/사례 적용 또는 미확인>

## 이번에 판단할 것
- 질문:
- 왜 필요한가 / 누가 답하나:
- 선택지와 결과 차이: <결정 질문일 때만>
- 추천과 이유: <근거 없으면 먼저 확인할 내용>
- 답이 바꾸는 작업 / 답 없이 가능한 작업:

## 다음 작업과 확인 방법
- 맡길 지시:
- 받을 결과:
- 직접 확인할 부분과 통과 기준:
- 실패하거나 모르면 할 일:

## 확인 지점 (최근 것이 위)

### 커밋 확인: M<n>-c<k>, <날짜 시각>
- 무엇을 어떻게 짰나: <파일별 역할, 데이터 흐름, 고른 설계>
- 검토 결과: <클린 코드 / 구조 / 보안 점검에서 걸린 것과 처리, 도구 실행 결과>
- 이해 질문: <설계 선택 1~3개. 이렇게 짰고 그래서 이렇게 됩니다, 이대로 갈까요?>
- 놓쳤을 수 있는 것: <최대 3개, 선택지와 추천>
- 커밋 메시지 초안:
- 내 결정 — 사용자 작성: <컨펌 / 수정, 한마디>

### 묶음 확인: M<n>.<a>~M<n>.<c>, <날짜 시각>
- 끝낸 작업:
- 볼 것: <경로, 테스트 결과>
- 놓쳤을 수 있는 것 (최대 3개, 없으면 없음): <질문 / 왜 / 선택지와 추천 / 답 없을 때 기본값>
- 규칙으로 남긴 내 기준: <내 원문 → AI가 따를 규칙, 틀렸으면 여기서 고쳐 주세요>
- 내 결정 — 사용자 작성: <계속 / 수정 / 중단>

### 지침과 안 맞음: <작업 번호>
- 어긋나는 곳: <AGENTS.md / README / 사용자 기준의 해당 문장>
- 선택지와 추천:
- 내 결정 — 사용자 작성:

## 내 피드백 — 사용자 작성
<사용자가 직접 작성. 기존 원문은 에이전트가 고쳐 쓰지 않음>

## 반영 결과 — 에이전트 작성
| 피드백 근거 | 이해한 내용 | 변경 전후와 이유 | 바뀐 문서/결과 | 검증 증거와 상태 |
|---|---|---|---|---|

- 후속 질문: <현재 답할 수 있는 중요한 질문만, 없으면 없음>
- 기술 검증: <미실행/통과/실패와 근거>
- 업무 수용: <미확인/실제 사용자 반응과 확인할 사람>
- 상세 문서: REQUIREMENTS.md / PLAN.md / AGENTS.md / HANDOFF.md
```

경량 모드에서는 이 내용을 HANDOFF.md 안의 짧은 절로 합칠 수 있다. 기존 사용자 피드백 문서를 없애거나 합의한 파일 위치를 임의 변경하지 않는다.

## 반영 순서

1. 최신 사용자 지시와 피드백을 읽고, 이전에 반영한 항목과 새 항목을 구분한다.
2. 실제 발언을 근거로 이해한 내용과 영향받는 작업을 정리한다. 중요한 해석이 두 가지면 그 부분만 확인한다.
3. 허용된 수정은 수행한다. 목적/범위/기준, 방법/검증, 지속 규칙, 현재 상태 중 무엇이 바뀌는지에 따라 상세 문서를 갱신한다.
4. 영향받은 검증을 수행한다. 문서 변경은 요구사항과 계획의 일치, 경로, 미확정 상태 보존을 확인하고, 구현 변경은 해당 동작을 실제 검증한다.
5. 변경 전후와 검증 결과를 짧게 보고한다. 검증 통과와 현업의 수용을 동일시하지 않는다.

새 요구사항이 없는데 같은 설명이나 승인을 반복 요청하지 않는다. 목표와 범위를 크게 바꾸는 선택, 업무 사실의 확인, 기존 권한 밖 행동은 해당 결정권자에게 확인한다.

피드백을 파일에 적기만 해서는 에이전트가 자동 실행되지 않는다. 사용자가 "피드백 반영해"라고 요청하거나, 이미 실행 중인 에이전트가 합의한 점검 시점에 읽는 방식이다.

# 사용자가 판단하고 에이전트가 작업하는 흐름

사용자는 문제를 이해하고 중요한 선택과 결과 수용을 맡는다. 에이전트는 자료 조사, 설명, 허용된 실행, 검증과 문서 갱신을 맡는다.

## 1. 시작: drill-pilot

`$drill-pilot 이 문제를 내가 이해하고 지휘할 수 있게 도와줘. 먼저 내 역할부터 확인해.`

- 사용자가 현업 담당자인지, 받은 요건을 구현하는 사람인지, 두 역할인지 먼저 확인한다. 업무 기준의 결정권도 따로 묻는다.
- 정리, 필요한 설명, 후속 질문을 최소 10턴 실제로 주고받는다. 1턴은 에이전트의 정리/질문과 사용자의 답변/선택/역질문 한 묶음이다.
- 사용자가 자신의 말과 사례로 설명한 근거를 통해 이해를 파악한다. 능력 점수나 형식적인 동의로 대신하지 않는다.
- 역질문은 개념 설명, 현업 기준 확인, 시험이 필요한 항목으로 나눠 처리한다.
- 10턴 이후 충분히 이해했다면 실제 발언 근거를 들어 계획 전환을 제안한다. 반복 질문과 근거 없는 예외 확장이 과한 요건 설계로 흐를 수 있음을 설명한다.
- 사용자의 명시적인 조기 종료나 계획 작성 요청은 우선한다. 대화 수를 채우기 위해 사용자 답을 만들어 내지 않는다.

사용자가 이미 이해하고 계획이나 구현을 직접 요청했다면 이 긴 대화를 강제하지 않는다. 스킬을 만드는 대화와 실제 과제 인터뷰도 구분한다.

## 2. 필요한 확인: drill과 gap-assist

- 실제 현업 흐름과 기준을 물어야 하면 `drill`을 쓴다. 사용자가 구현자이면 담당자에게 보낼 질문지를 만들 수 있다.
- 선택의 의미나 빠진 부분을 설명받아야 하면 `gap-assist`를 쓴다. 문제 상황, 선택지, 추천 이유, 결정권자를 함께 본다.
- 두 스킬은 필요할 때만 쓴다. 사용자가 이미 답한 내용과 자료로 확인 가능한 사실을 다시 묻지 않는다.

## 3. 계획: problem-discovery

`$problem-discovery 지금까지의 사용자_검토.md와 대화를 바탕으로 계획과 인계 문서를 만들어줘.`

표준 모드에서는 다음 다섯 문서를 만든다. 작은 작업은 한 문서에 합칠 수 있다.

| 문서 | 역할 |
|---|---|
| 사용자_검토.md | 사람이 먼저 읽는 안내. 현재 상태, 선택, 다음 작업, 확인 방법, 피드백 |
| REQUIREMENTS.md | 목적, 범위, 요구사항과 성공 기준 |
| PLAN.md | 방법, 작업 순서, 검증과 변경 이유 |
| AGENTS.md | 지속적으로 따를 권한, 제약, 피드백 처리 규칙 |
| HANDOFF.md | 진행 상태, 남은 질문, 다음 행동 |

drill-pilot에서 확인한 역할과 이해의 근거는 이어받는다. 새로운 10턴 인터뷰를 시작하지 않는다. problem-discovery의 추가 질문은 현재 계획을 바꾸는 핵심 항목에 집중한다.

## 4. 실행과 피드백

1. 사용자는 사용자_검토.md에서 이번에 결정할 것과 다음 작업을 확인한다.
2. 사용자의 실행 지시가 있으면 에이전트는 합의된 범위에서 작업하고 검증한다.
3. 사용자가 결과를 보고 피드백을 적거나 대화로 전달한다.
4. 에이전트는 원문과 해석을 구분하고, 영향받는 문서와 결과를 갱신한다.
5. 변경 전후, 이유, 실제 검증 증거, 남은 질문을 돌려준다.

`사용자_검토.md에 적은 피드백을 반영해줘. 관련 문서와 결과를 수정하고 검증 결과를 알려줘.`

이 지시는 현재 허용된 작업 범위 안에서 처리한다. 문서 수정이 구현, 외부 전송, 배포까지 허용하는 뜻은 아니다. 이미 허용된 명확한 수정은 같은 허락을 다시 묻지 않는다.

파일을 저장하기만 해서는 에이전트가 실행되지 않는다. 반영을 요청하거나, 실행 중인 작업의 합의한 점검 시점에 읽게 한다. 사용자 직접 작성 영역과 기존 판은 프로젝트 규칙에 따라 보존한다.

## 5. 줄이려는 병목

| 병목 | 이 흐름에서의 대응 |
|---|---|
| 인지 | 역할에 맞춘 설명과 최소 10턴 이해 대화, 짧은 사용자 안내 |
| 입력 | 기존 자료와 답변 재사용, 필요한 정보만 요청 |
| 판단 | 선택 차이와 추천 이유 제공, 결정권자 구분 |
| 실행 | 선택을 작업 지시로 전환, 권한 안의 반복 작업은 에이전트가 처리 |
| 검증 | 통과 기준을 먼저 정하고 실제 확인 증거를 제시 |
| 수용 | 대표 업무에 적용해 본 실제 반응을 받아 다음 수정에 반영 |

기술 검증 통과와 현업의 수용은 별도 상태로 기록한다. 빈 피드백은 동의가 아니며, 사용자 이해와 담당자 정책을 추정으로 확정하지 않는다.

## 6. 이 흐름이 잘 작동하는지 확인하는 기준

- 사용자가 목적, 중요한 선택, 다음 행동을 자기 말로 설명할 수 있는가?
- 결정에 필요한 정보와 확인할 담당자가 드러나 있는가?
- 피드백이 무엇을 바꿨는지 문서와 실제 결과에서 확인되는가?
- 사용자가 결과를 받아들일 근거와 남은 한계를 알 수 있는가?

대화, 검증 결과, 현업 반응을 지어내서 기록을 채우지 않는다.

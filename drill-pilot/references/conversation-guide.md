# 정리와 질문의 티키타카

이 파일은 사용자가 문제를 설명하기 어려워하거나, 후속 질문과 계획 전환의 표현이 필요할 때 읽는다. 아래 예시는 실제 대화 횟수로 계산하지 않는다.

## 첫 10회 대화의 방향 예시

각 행은 질문의 후보이며 정해진 순서가 아니다. 사용자의 답에서 이미 확인된 것은 반복하지 않고, 다른 중요한 축이나 실제 사례 적용으로 넘어간다. 한 응답에서 여러 항목을 설명했어도 실제 대화 횟수는 한 번이다.

| 회차 예시 | 대화의 초점 | 질문이나 정리 예 |
|---|---|---|
| 1 | 역할과 결정권 | 직접 업무를 하는 분인가요, 받은 요건을 구현하는 분인가요? 업무 기준을 확정하는 사람은 누구인가요? |
| 2 | 현재의 이해 | 받은 요청이나 현재 문제를 본인이 이해한 말로 설명해 주세요. 애매한 부분은 그대로 알려 주세요. |
| 3 | 목적과 결과의 사용 | 결과를 받는 사람은 그것을 보고 무엇을 결정하거나 처리하나요? |
| 4 | 실제 사례 | 최근 한 건에서 어떤 자료를 받아 무엇을 했나요? 직접 경험하지 않았다면 받은 설명이나 예시를 기준으로 알려 주세요. |
| 5 | 입력과 근거 | 방금 설명에서 자료로 확인한 부분과 아직 추정인 부분을 나눠 볼까요? |
| 6 | 결과를 확인하는 기준 | 결과가 제대로 나왔는지 직접 확인하려면 무엇을 보겠어요? 회사 기준을 모르면 확인할 사람을 함께 정하면 됩니다. |
| 7 | 중요한 선택 | A와 B는 이런 차이가 있습니다. 현재 목적에는 어느 쪽이 맞고, 어떤 점을 포기할 수 있나요? |
| 8 | 대표적인 실패나 예외 | 실제로 가장 곤란했던 경우 하나가 있나요? 사례가 없다면 어떤 실패를 먼저 확인해야 할지 함께 골라 보겠습니다. |
| 9 | 결정과 위임의 경계 | 여기까지 중 직접 정할 것과 담당자에게 확인할 것은 무엇인가요? 제가 조사할 수 있는 항목은 제가 맡겠습니다. |
| 10 | 자기 말로 연결하기 | 이제 이 작업의 목적, 받을 결과, 확인할 기준을 동료에게 어떻게 설명하시겠어요? 모르는 부분과 다음 행동도 함께 정리해 주세요. |

10회차 답변을 받은 뒤 충분한 이해의 근거가 있으면 전환을 제안한다. 단순히 열 번째 질문을 출력한 상태에서 "10턴 완료"라고 쓰지 않는다.

## 설명 수준 조절

- 현업이 업무는 잘 알고 기술 용어를 모르면 기술 설명을 보충한다. 업무 목적을 처음부터 반복해서 묻지 않는다.
- 구현자가 기술은 잘 알고 현장 기준을 모르면 업무 사실과 정책의 확인 경로를 만든다. 기술 퀴즈로 이해도를 대신 측정하지 않는다.
- 설명을 들은 직후 "이해했나요?" 대신 같은 사례의 선택이나 결과에 적용해 본다.
- "왜 그렇게 생각하나요?"를 매번 반복하지 않는다. 사용자가 이미 이유를 말했다면 그 이유를 받아 정리한다.
- 역질문이 타당한 반박이면 에이전트의 해석이 틀렸을 가능성부터 확인한다.

## 역질문 예: 처리율의 분모

사용자: "반려된 신청 건은 처리율 분모에서 빼는 게 맞는 거야?"

응답 예:

> 이건 지금 자료만으로 회사의 기준을 정할 수는 없습니다. 접수한 건을 얼마나 끝냈는지 보려는지, 정상 신청만 놓고 처리 속도를 보려는지에 따라 지표가 달라집니다.
> 담당자에게는 '현재 월간 실적 보고에서 반려 건은 어떻게 반영하나요?'라고 확인하면 됩니다. 답을 받기 전에도 상태별 건수는 조사할 수 있습니다.
> 이번 결과를 보는 사람이 우선 판단하려는 것은 업무량인가요, 처리 속도인가요? 전달받은 요청에 이 부분이 있었나요?

이 질문으로 사용자의 목적 이해를 돕는다. 회사의 공식 정의를 사용자가 임의로 선택하도록 유도하지 않는다.

## 중간 정리 예

> 지금까지는 사용 목적과 결과를 쓰는 장면을 직접 설명하셨습니다. 입력의 출처도 구분됐습니다. 다만 어느 정도 차이를 중요한 문제로 볼지는 현업 기준이 아직 없습니다. 다음에는 그 기준을 누가 정하고 어떤 사례로 확인할지 짚겠습니다.

정리의 근거는 실제 발언이어야 한다. 이 문장을 상황과 무관하게 재사용하지 않는다.

## 이해 상태 기록 예

| 축 | 현재 상태 | 실제 대화 근거 | 남은 일 |
|---|---|---|---|
| 목적과 사용자 | 스스로 설명함 | 사용자의 관련 발언을 짧게 인용하거나 정확히 요약 | 해당 없으면 없음 |
| 업무와 입력 | 설명 후 사례에 적용함 | 사용자가 적용한 사례 | 출처 확인이 남으면 기록 |
| 성공과 검증 | 추가 확인 필요 | 어떤 부분을 모른다고 했는지 | 확인할 사람과 질문 |

이 표는 형식 예시다. 실제로 관찰하지 않은 상태를 채우지 않는다. 상태가 바뀌면 어떤 설명이나 사례가 도움이 됐는지 남긴다.

## 계획 전환 예

아래 상황이 실제로 확인됐을 때만 사용한다.

> 이제 계획을 세울 만큼 정리됐습니다. 사용 목적을 직접 설명하셨고, 두 비교 방식의 차이를 사례에 적용하셨으며, 공식 기준은 담당자에게 확인해야 한다는 점도 구분하셨습니다.
> 남은 것은 기준 확인과 작은 데이터 점검으로 풀 수 있습니다. 여기서 화면의 모든 예외와 미래 기능까지 정하면 현재 목적보다 요구사항이 커질 가능성이 높습니다. 이쯤에서 계획 초안으로 넘어가는 것을 권합니다.

끝에 다음 행동을 선택할 수 있게 한다. 이미 사용자가 계획 작성을 지시했다면 재질문하지 않는다.

## 경계 상황에서의 행동

| 상황 | 기대 행동 |
|---|---|
| 3턴 만에 핵심 이해가 충분해 보임 | 충분하다고 보는 근거를 짧게 말하고 "사례 적용으로 10턴까지 이어 갈지, 지금 계획으로 넘어갈지" 고르게 함. 이어 가면 새 요구사항을 발명하지 않음 |
| 4턴에 사용자가 "질문은 그만하고 계획 써"라고 함 | 최소 10턴 규칙보다 현재 지시를 우선. 남은 모름을 표시하고 계획 작성 |
| 역할이 구현자이고 공식 업무 기준은 모름 | 이해 부족으로 몰지 않고 담당자 확인 항목과 답 없이 할 수 있는 작업을 구분 |
| 사용자가 기술 용어를 되물음 | 설명부터 제공. 현업 인터뷰 항목을 무조건 추가하지 않음 |
| 10턴 후에도 목적이나 핵심 판단을 설명하기 어려움 | 부족한 축에 집중해서 대화 계속. 턴 수만으로 완료 선언하지 않음 |
| 10턴 이후 질문이 같은 선택의 재확인에 머묾 | 반복된 부분과 남은 질문의 낮은 영향을 근거로 계획 전환 제안 |
| 예시 대화를 만들어 달라는 요청 | 예시임을 밝힘. 실제 사용자 이해나 완료 턴 수의 근거로 쓰지 않음 |
| 다른 세션에서 이어받았으나 대화 횟수 증거가 없음 | 완료 횟수는 미확인으로 기록하고 최소한의 진행 맥락을 확인. 임의로 10턴을 채웠다고 하지 않음 |

# Crew

| 역할 | 하는 일 | 기본 수 |
|---|---|---|
| 킥오프 | 문제 수준을 보고 편성을 정하고, 사용자와 대화해 요구사항, 계획, 세션별 지시와 병렬 방식을 정한다. 실행하지 않는다 | 처음 1번 |
| 작업 | 산출물을 만드는 긴 작업. 사용자 지시에 근거한 수정 요청을 검토해 반영하거나, 아니면 사용자를 설득한다 | 1 (병렬이면 2~3) |
| 노티 | 작업을 지켜보고 판단해 지시와 어긋나면 수정 요청, 사용자가 알아야 할 것은 알린다 | 1 |
| 기록 | working_raw_log와 지시/요청/응답을 사람이 읽을 history로 정리한다 | 1 |

**권한의 원천은 사용자 하나다.** 노티가 스스로 판단한 개선안은 작업에 바로 가지 않고 사용자 승인을 거친다. 그래야 두 에이전트가 서로 고치다 사용자 의도에서 멀어지지 않는다.

역할 정보는 어떤 `AGENTS.md`에도 쓰지 않는다. `AGENTS.md`는 그 폴더의 모든 세션이 자동으로 읽으므로, 역할을 적으면 모든 세션이 같은 역할을 받는다. 역할은 이 스킬과 `_crew/역할.md`로만 정한다.

## 0. 역할부터 정한다

이 스킬로 시작한 세션은 **다른 무엇보다 먼저** 역할을 정한다. 첫 메시지에 작업 지시가 있어도 역할이 정해지기 전에는 시작하지 않는다. 그 지시는 역할이 정해진 뒤 `_crew/지시.md`에 옮긴다.

1. 작업 폴더에서 `_crew/역할.md`와 `_crew/EXECUTION.md`를 찾아 읽는다(읽기만).
2. 묻는다.

```
이 세션의 역할을 정해 주세요.
0. 킥오프: 과제를 보고 대화로 요구사항, 계획, 세션별 지시를 먼저 정함
1. 작업: 산출물을 만드는 긴 작업
2. 노티: 작업을 지켜보고 판단해 알림, 지시와 어긋나면 수정 요청
3. 기록: 로그를 history로 정리
4. 직접 지정
현재: <역할.md 기준 사용 중인 역할, 없으면 "없음">
추천: <아래 규칙>
```

추천 규칙:
- `EXECUTION.md`가 없다: **0. 킥오프**
- 있다: EXECUTION.md 편성표에서 아직 아무도 맡지 않은 세션 중 맨 위. 그 세션의 시작 지시문도 함께 보여 준다.

3. 턴을 끝내고 답을 기다린다.
4. 답을 받으면 `_crew/`가 없을 때 [references/board.md](references/board.md) 양식으로 만들고, `역할.md`에 자기 줄을 추가한 뒤 해당 역할 파일을 읽고 시작한다.

- 이미 사용 중인 역할을 고르면 겹친다고 알린다. 같은 역할 둘은 같은 파일을 쓰게 된다. 그래도 원하면 범위를 나눠 `작업-B`처럼 등록한다.
- 세션을 다시 켜서 이어 가면 `역할.md`의 자기 줄 상태를 갱신한다.

| 역할 | 지침 |
|---|---|
| 킥오프 | [references/role-kickoff.md](references/role-kickoff.md) |
| 작업 | [references/role-worker.md](references/role-worker.md) |
| 노티 | [references/role-noti.md](references/role-noti.md) |
| 기록 | [references/role-history.md](references/role-history.md) |
| 직접 지정 | 사용자 설명을 역할.md에 적고 아래 공통 규칙을 따른다 |

## 1. 공유 폴더 `_crew/`

세션끼리는 직접 대화할 수 없다. 이 폴더의 파일이 유일한 통로다. 양식은 [references/board.md](references/board.md).

| 파일 | 내용 | 쓰는 쪽 | 방식 |
|---|---|---|---|
| 역할.md | 세션 등록과 상태 | 각 세션이 자기 줄 | 추가, 자기 줄만 갱신 |
| REQUIREMENTS.md, PLAN.md, EXECUTION.md | 킥오프 결과 | 킥오프 | 덮어쓰기 |
| 지시.md | 사용자 지시 원장 (D-번호, 원문 그대로) | 지시를 받은 세션 | 끝에 추가만 |
| working_raw_log.md | 작업 과정 원본 로그 | 작업 | 추가만 |
| 상태.md | 지금 단계, 다음 행동, 막힌 것 | 작업 | 덮어쓰기 |
| 요청.md | 수정 요청 (C-번호, 근거 D-번호) | 노티 | 추가만 |
| 응답.md | 요청에 대한 판정과 이유 | 작업 | 추가만 |
| 노티.md | 사용자에게 보낸 알림 | 노티 | 추가만 |
| history.md | 사람이 읽는 정리본 | 기록 | 덮어쓰기 |

- 파일마다 쓰는 쪽은 하나다. 지시.md만 예외로, 지시를 받은 세션이 끝에 추가한다. 남의 파일은 읽기만 한다.
- 작업이 여러 레인이면 작업 파일에 레인 이름을 붙인다: `working_raw_log-A.md`, `상태-A.md`, `응답-A.md`.
- 추가만 하는 파일은 이미 쓴 줄을 고치거나 지우지 않는다. 정정은 새 줄로.
- 시각은 `YYYY-MM-DD HH:MM`.

## 2. 공통 규칙

- 사용자가 어느 세션에 말하든 지시는 원문 그대로 `지시.md`에 D-번호로 남긴다. 이게 없으면 "사용자 지시에 따른 요청인가"를 판정할 수 없다.
- 기다릴 때는 파일이 바뀔 때까지 잠든다. 계속 읽으며 돌지 않는다.
  ```
  python3 <이 스킬 폴더>/scripts/wait_change.py --state _crew/.wait-<역할>.json --timeout 600 <파일들>
  ```
  지난번 이후 바뀐 파일과 새로 붙은 줄만 출력한다. 전체를 다시 읽지 않는다. `--timeout`은 도구 실행 시간 제한보다 짧게 잡는다.
- 대화가 길어지면(요청과 응답이 수십 차례 오가면) 상태를 자기 파일에 남기고 사용자에게 세션 재시작을 권한다. 긴 대화가 토큰을 가장 많이 먹는다. 재시작한 세션은 `$crew`로 같은 역할을 고르면 파일에서 이어 간다.
- 사용자 알림은 노티만 보낸다. 다른 역할이 알릴 일이 생기면 자기 파일에 적고, 노티가 읽어 전달한다.

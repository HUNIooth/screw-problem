# 킥오프

목표: 사용자와 대화해 **과제 README의 필수 요구사항이 하나도 빠지지 않는** 요구사항, 계획, 세션별 실행 지시를 만든다. 다음 세션들은 EXECUTION.md의 지시문만 붙여 넣으면 바로 일할 수 있어야 한다.

실행하지 않는다. 문서와 편성까지가 끝이다.

## 1. 읽기

- 과제 README(또는 요구사항 문서, 공고, 메일). 사용자가 경로를 안 줬으면 작업 폴더의 `README*`를 찾고, 없으면 묻는다.
- 작업 폴더 구조, 주어진 데이터와 코드, 제출 형식, 평가 기준.
- `사용자_검토.md`나 drill-pilot, problem-discovery 결과가 있으면 먼저 읽고, 이미 받은 답은 다시 묻지 않는다.
- README의 **필수 요구사항 문장을 원문 그대로** 뽑는다. "~해야 한다", "필수", "반드시", "제출물", 평가 항목이 신호다. 해석은 나중에 하고, 먼저 원문을 빠짐없이 모은다.

## 2. 문제 수준과 편성

| 수준 | 기준 | 편성 |
|---|---|---|
| S | 한 세션으로 반나절 안쪽, 산출물 하나 | crew가 필요 없다고 말하고 한 세션으로 하라고 권한다 |
| M | 하루 안팎, 산출물이 하나로 이어짐 | 작업 1 + 노티 1 (기록은 노티가 짧게 겸하거나 생략) |
| L | 여러 날, 결정이 자주 바뀜 | 작업 1 + 노티 1 + 기록 1 (기본) |
| XL | 서로 다른 파일로 나뉘는 독립 산출물 여럿 | 작업 레인 2~3 + 노티 1 + 기록 1 |

- 작업 레인을 나누는 조건: 레인끼리 **같은 파일을 고치지 않는다.** 나눌 수 없으면 레인 하나로 간다. 같은 파일을 두 세션이 고치면 합칠 때 드는 비용이 병렬로 아낀 시간보다 크다.
- 레인은 3개까지, 그리고 설정의 동시 상한 안에서. 노티 하나가 지켜볼 수 있는 양에 한계가 있다.
- 세션마다 쓸 모델은 설정의 '모델: 계획과 검토'(킥오프, 노티)와 '모델: 구현'(작업, 기록)을 따른다.
- 수준과 편성을 한 줄 이유와 함께 사용자에게 제안한다.

## 3. 대화

질문은 라운드로 한다. 한 라운드 최대 5개, 질문마다 왜 묻는지와 추천 답을 붙이고, 보냈으면 턴을 끝내고 기다린다.

- 결정 질문(해석, 편성, 우선순위)은 실제로 다른 결과를 내는 선택지를 3개 이상 주고 하나를 추천한다. 진짜 2개뿐이면 2개. 항상 '직접 입력'을 둔다.
- 사실 질문(마감 날짜, 제출 위치, 경로)은 선택지 없이 열어서 묻는다. 지어낸 선택지는 틀린 사실을 불러온다.

먼저 물을 것:
- README 문장 중 해석이 갈리는 것 (두 해석을 나란히 보여 주고 추천)
- 평가 기준과 배점에서 무엇이 가장 중요한가
- 마감, 제출 형식, 제출 위치
- 쓰면 안 되는 것 (외부 API, 특정 라이브러리, 사람 손)
- 편성 제안에 대한 동의

조사로 알 수 있는 건 묻지 않는다. 사용자 답은 원문 그대로 `지시.md`에 D-번호로 남긴다.

## 4. 문서 쓰기

양식은 [board.md](board.md).

**작업 설정**: 대화 첫 라운드에 이 과제의 역할(내 문제 / 현업 요건 구현)과 결정권자, 이번 제약을 확인해 `_crew/사용자_검토.md` 맨 위에 적는다.

**REQUIREMENTS.md**
- README 필수 요구사항 추적표: R-번호, README 원문, 해석, 검증 방법, 담당 레인, 근거(D-번호).
- README에 없지만 필요한 것, 범위 밖.

**PLAN.md**
- 메이저 기능(M1, M2...)과 마이너 작업(M1.1...)으로 잘게 나눈다. 마이너는 한 가지 일이면서 테스트로 통과를 판정할 수 있는 크기.
- 메이저마다 커밋 분기점 2개 이상, 분기점마다 사람이 볼 것과 계속/수정/중단 기준. 나눌 자리가 갈리면 사용자에게 선택지와 추천으로 묻는다.
- 마이너마다 통과 기준, 선행 작업, 담당 레인.
- `problem-discovery` 스킬이 설치돼 있으면 그 `references/review/` 점검표 세 개를 `_crew/review/`로 복사한다. 없으면 작업 세션은 자기 지침의 다섯 줄 점검만 한다.
- 위험한 모름은 맨 앞 시험 단계로.

**EXECUTION.md**
- 편성표: 세션, 역할, 범위, 소유 파일과 폴더, 담당 요구사항, 시작 조건.
- 병렬과 순서: 동시에 돌릴 단계, 기다려야 하는 단계와 그 이유, 합류 지점과 통합 담당, 통합 검증 방법.
- 세션별 시작 지시문: 사용자가 새 세션에 그대로 붙여 넣을 문장. `$crew`와 역할 이름, 절대경로, 맡을 범위, 하지 말 것을 넣는다.
- 노티 감시 포인트: 요구사항별로 무엇을 보면 어긋난 것인지.
- 기록 정리 주기.

## 5. 마지막 점검

- [ ] README 필수 요구사항이 모두 R-번호를 받았다 (원문 개수와 R 개수를 대조)
- [ ] 모든 R에 검증 방법과 담당 레인이 있다
- [ ] 메이저마다 커밋 분기점이 2개 이상이고, 마이너마다 통과 기준이 있다
- [ ] 모든 레인에 담당 R이 있다 (아무 요구사항도 안 맡은 레인은 없앤다)
- [ ] 레인끼리 소유 파일이 겹치지 않는다
- [ ] 시작 지시문이 이 대화를 못 본 세션에서도 통한다 (절대경로, 대화에서만 쓴 말 없음)

빠진 것이 있으면 문서를 고치고 다시 점검한다.

## 6. 넘기기

`_crew/사용자_검토.md`를 처음 쓴다: 목적, 편성, 지금 정할 것, 첫 확인 지점이 언제인지. 사람은 이 한 장만 보면 되게 쓴다.

사용자에게 알린다.
- 문제 수준, 편성, 이유 한 줄
- 세션을 여는 순서 (보통 작업 먼저, 기록은 작업 로그가 쌓인 뒤)
- 각 세션에 붙일 지시문은 EXECUTION.md의 어느 절에 있는지
- 남은 추정과 사용자 결정 대기

그리고 **이 세션을 노티로 전환**할지 묻는다. 계획을 가장 잘 아는 세션이 감시를 맡는 편이 낫다. 동의하면 `역할.md`의 자기 줄을 노티로 바꾸고 [role-noti.md](role-noti.md)를 읽는다.

마지막 줄은 상태줄(✅ 완료 / ⏳ 진행 중 / 🛑 결정 필요).

# Gap Assist

목표: 빈 곳을 지적하는 데서 끝내지 않고, **상대가 바로 결정할 수 있게** 알려 준다.

"예외 처리가 없습니다" 같은 지적은 상대가 그 주제를 모르면 쓸모가 없다. 현업과 기획자는 무엇을 모르는지 모르는 경우가 많다. 그래서 빈 곳마다 이대로 가면 생기는 장면을 보여 주고, 보통 고르는 선택지와 추천을 붙인다.

## 1. 대상과 읽는 사람

- **대상**: 파일 경로나 붙여 넣은 글. drill의 `요건정리.md`, problem-discovery의 `REQUIREMENTS.md`면 그 칸 구조대로 읽는다.
- **읽는 사람**: 현업 / 기획자(사용자 본인) / 수행 에이전트. 설명 수준과 말투가 달라진다. 불분명하면 사용자 본인으로 둔다.
- 대상이 무엇을 하려는 건지 한 줄로 요약해 맨 앞에 보여 준다. 요약이 틀리면 점검 전체가 틀리므로, 사용자가 고칠 수 있게 드러내 둔다.

## 2. 빈 곳 찾기

[references/blind-spots.md](references/blind-spots.md) 점검표로 훑는다. 대상 유형에 맞는 영역만 깊이 본다.

빈 곳은 세 종류로 나눈다.
- **없음**: 다뤄야 하는데 아예 없다
- **모호함**: 있지만 검증할 수 없다("빠르게", "적절히", "필요시")
- **충돌**: 두 곳이 서로 다른 말을 한다

사실 확인으로 풀리는 것(작업 폴더 파일, 데이터, 공개 자료)은 직접 확인해 채우고 출처를 단다. 사내 규정이나 내부 결정처럼 내가 알 수 없는 것은 지어내지 않고 "확인 필요(누구에게)"로 둔다.

## 3. 순위

- **치명**: 이대로 가면 결과물이 틀리거나 못 쓴다, 또는 규정 위반
- **중요**: 나중에 고치면 비용이 크다
- **참고**: 있으면 좋다

본문에는 치명과 중요만, 최대 7개. 참고는 끝에 한 줄씩. 지적이 너무 많으면 아무것도 안 고친다.

## 4. 알려 주기

빈 곳마다 이 형식으로 쓴다.

```
[치명] G1. <빈 곳 한 줄>
- 위치: <문서의 어느 부분, 또는 "없음">
- 왜 문제: <이대로 가면 생기는 구체적 장면>
- 보통 이렇게 정한다:
  A. <선택지>: <언제 맞나>
  B. <선택지>: <언제 맞나>
  C. <선택지>: <언제 맞나>
- 추천: <하나와 이유>
- 누가 정하나: <현업 / 사용자 / 확인 필요(부서)>
```

- 읽는 사람이 모를 법한 개념이면 '왜 문제' 앞에 한두 줄로 풀어 쓴다. 비유보다 실제 예를 든다.
- 현업용이면 IT 용어를 쓰지 않는다.
- 선택지는 3개 이상이 기본이다. 실제로 다른 결과를 내는 것만 넣고, 진짜 2개뿐이면 2개로 둔다.
- 추천은 하나만 한다. 판단 근거가 부족하면 "~를 알면 정할 수 있음"이라고 쓴다.
- "보통 이렇게 정한다"에 근거 없는 업계 관행을 단정하지 않는다. 일반론이면 일반론이라고 쓴다.

## 5. 마무리

- **바로 물어볼 질문** 목록을 붙인다. 현업에게 보낼 문장으로 써서 drill 다음 회차에 그대로 쓸 수 있게 한다.
- 결과가 길면 대상 파일 옆에 `보완안내.md`로 저장하고, 짧으면 대화로 끝낸다.
- 사용자가 "반영해"라고 하기 전에는 원문을 고치지 않는다. 반영할 때는 원본을 남기고 새 판으로 만든다.
- 다음 단계 제안: 현업에게 더 물어야 하면 `$drill`, 정리가 끝났으면 `$problem-discovery`.
- 마지막 줄은 상태줄(✅ 완료 / ⏳ 진행 중 / 🛑 결정 필요).

## 하지 말 것

- 문장 다듬기나 오탈자 지적으로 지면 채우기
- 선택지 없이 "정의 필요"만 적기
- 근거 없이 "업계에서는 보통"이라고 단정하기
- 지적을 수십 개 늘어놓기
- 허락 없이 원문 고치기

# screw-problem

처음 보는 개발 과제(앱, 업무 자동화, 데이터 처리)를 만났을 때 쓰는 Codex 스킬 모음입니다. 내가 먼저 문제를 이해하고, 계획은 AI가 세우고, 개발하는 동안에도 내 지식과 방향이 AI에 녹아들어 내가 제어할 수 있게 합니다. Claude Code에서도 같은 폴더를 그대로 쓸 수 있습니다.

| 스킬 | 언제 쓰나 |
|---|---|
| `screw-setup` | 처음 한 번. 역할, 모델, 멀티에이전트, 공통 제약 설정 |
| `drill-pilot` | 문제를 내가 먼저 제대로 이해하고 싶을 때 |
| `drill` | 현업 담당자에게 실제 업무와 요건을 물어야 할 때 |
| `gap-assist` | 기획안이나 요건 정리에 빠진 게 없는지 볼 때 |
| `problem-discovery` | 요구사항, 계획, 다른 에이전트에게 넘길 문서를 만들 때 |
| `crew` | Codex 세션 여러 개에 역할을 나눠 같이 돌릴 때 |

## 원칙

**사람이 보는 문서는 `사용자_검토.md` 한 장입니다.** 스킬이 만드는 다른 문서(REQUIREMENTS, PLAN, AGENTS, HANDOFF, `_crew/` 안의 파일)는 AI가 읽고 쓰는 문서라 열어 볼 필요가 없습니다. 내가 알아야 하거나 정해야 하는 것은 모두 이 한 장에 올라옵니다.

**계획은 메이저 기능과 마이너 작업으로 잘게 나뉩니다.** 마이너 작업은 한 가지 일이면서 테스트로 통과를 판정할 수 있는 크기입니다.

**AI는 정해진 자리에서 멈춥니다.** 멈추면 `사용자_검토.md`에 올리고 내 답을 기다립니다. 확인 없이 넘기고 싶은 범위가 있으면 미리 말해 두면 됩니다.

| 언제 | AI가 하는 일 | 내가 하는 일 |
|---|---|---|
| 마이너 작업 3개를 끝낼 때마다 | 한 일, 볼 것, 놓쳤을 수 있는 것 정리 | 계속, 수정, 중단 중 하나로 답 |
| 마이너 작업이 지침이나 README와 안 맞을 때 | 어디가 어긋나는지와 선택지 제시 | 고르기 |
| 메이저 기능의 커밋 분기점 (기능당 최소 2번) | 검토 후 무엇을 어떻게 짰는지 설명하고 설계 선택을 질문 | 이해하고 컨펌하면 그때 커밋 |

커밋 분기점은 AI가 정하고, 나눌 자리가 애매하면 나에게 선택지를 주고 묻습니다. 커밋 분기점이 3개 묶음과 겹치면 한 번만 멈춥니다. 한 번 멈출 때 나에게 오는 질문은 종류를 합쳐 최대 3개입니다.

**AI가 거꾸로 묻습니다.** 확인 지점마다 내가 말하지 않았지만 결과를 바꿀 만한 것을 최대 3개까지 묻습니다. 작업하다 실제로 발견한 것만 묻습니다. 어느 쪽으로 할지 정하는 질문에는 선택지와 추천이 붙어 있어 고르기만 하면 되고, 실제 사례나 값을 묻는 질문에는 아는 대로 적거나 자료를 알려 주면 됩니다.

**내 답은 규칙으로 남습니다.** 내가 답하거나 고쳐 준 것 중 다음에도 적용될 것은 AI가 따르는 지침(`AGENTS.md`)에 규칙으로 쌓이고, 무엇을 규칙으로 남겼는지 `사용자_검토.md`에 보여 줍니다. 잘못 이해했으면 거기서 바로 고치면 됩니다.

**만들 때는 정해진 방식으로 만듭니다.** 코드는 테스트를 먼저 쓰고, 버그는 원인을 확인한 뒤 고치고, 실제로 돌려 본 결과 없이 "됐다"고 하지 않습니다. 이 작업 방식은 [Superpowers](https://github.com/obra/superpowers)를 참고했습니다.

**커밋 전에 검토합니다.** 클린 코드, 구조(층 분리, CRUD 분리, 스파게티 방지), 보안 점검표로 변경분을 봅니다. 점검표는 지침 파일을 짧게 유지하려고 `review/` 폴더에 따로 두고, 커밋할 때만 읽습니다. 보안 치명 항목이 걸리면 커밋하지 않습니다.

## 설치

```bash
git clone https://github.com/HUNIooth/screw-problem.git
cp -R screw-problem/{screw-setup,drill-pilot,drill,gap-assist,problem-discovery,crew} ~/.codex/skills/
```

Claude Code에서도 쓰려면 바로가기를 하나씩 만듭니다.

```bash
for s in screw-setup drill-pilot drill gap-assist problem-discovery crew; do
  ln -s ~/.codex/skills/$s ~/.claude/skills/$s
done
```

설치 후 Codex를 다시 열고, 처음 한 번은 설정부터 합니다.

```
$screw-setup
```

환경(python3, git, 현재 모델, 멀티에이전트 기능)을 점검한 뒤 다섯 가지를 한 번에 묻습니다. 이 스킬들을 써 본 적 있는지, 평소 내 문제를 푸는지 현업 요건을 구현하는지, 계획과 구현에 쓸 모델, 멀티에이전트 허용 여부, 모든 작업에 지킬 제약. 답은 `~/.screw-problem/설정.md`에 남고, 다른 스킬은 이 값을 기본값으로 씁니다. "전부 추천대로"라고 해도 됩니다.

새 과제를 시작할 때마다 이번 문제가 누구의 것인지(내 문제인지 현업 요건인지)와 이번에만 더해지는 제약을 먼저 확인합니다. 설정과 같으면 "그대로"로 넘어갑니다.

그다음부터 `$스킬이름`으로 부를 수 있습니다. 이름을 안 불러도 "요구사항 정리해 줘", "현업 인터뷰 질문지" 같은 말에 알아서 켜집니다.

## 쓰는 법

### 문제를 먼저 이해하고 싶을 때: drill-pilot

```
$drill-pilot 이번 과제를 내가 이해하고 지휘할 수 있게 같이 정리해 줘
```

먼저 내가 현업 담당자인지, 요건을 받아 만드는 사람인지, 결정권이 누구에게 있는지를 묻습니다. 그다음 한 번에 질문 하나씩 주고받으며 목적, 실제 사례, 확인 기준을 정리합니다. 기본은 10번 정도 주고받는 것이고, 그 전에 충분해지면 계속할지 계획으로 넘어갈지 물어봅니다. "그만하고 계획 써"라고 하면 바로 넘어갑니다.

### 현업에게 물어볼 게 있을 때: drill

```
$drill 고객 문의 처리 담당자 인터뷰 질문지 만들어 줘. 30분짜리야
$drill 이 회의록을 요건으로 정리해 줘: ./회의록_1103.md
```

세 가지로 씁니다. 현업과 직접 대화하기, 사람이 들고 갈 질문지 만들기, 회의록이나 메모를 요건으로 정리하기. 의견을 묻기보다 최근에 실제로 처리한 한 건을 따라가며 판단 기준과 예외를 끌어냅니다. 결과는 `drill/날짜_업무명/요건정리.md`에 남고, 현업이 한 말은 원문 그대로 둡니다.

### 빠진 게 없는지 볼 때: gap-assist

```
$gap-assist ./기획안.md 빠진 거 없는지 봐 줘. 현업한테 보낼 거야
```

빠진 곳마다 이대로 가면 무슨 일이 생기는지, 보통 어떤 선택지가 있는지, 무엇을 추천하는지, 누가 정해야 하는지를 알려 줍니다. 중요한 것만 7개까지 보여 주고, 끝에 현업에게 바로 보낼 질문 목록을 붙입니다. 원문은 "반영해"라고 하기 전에는 고치지 않습니다.

### 계획과 인계 문서를 만들 때: problem-discovery

```
$problem-discovery 팀 주간 업무보고를 자동으로 만들고 싶어
```

묻기 전에 작업 폴더의 자료부터 찾아보고, 확인된 것과 모르는 것, 추정한 것을 나눠 보여 줍니다. 꼭 내가 정해야 하는 것만 한 번에 3개까지 묻고, 질문마다 선택지와 추천 답을 붙입니다. "알아서 해"라고 하면 추천대로 갑니다.

다 정해지면 `discovery/날짜_주제/`에 문서를 만듭니다.

| 파일 | 내용 | 누가 보나 |
|---|---|---|
| `사용자_검토.md` | 지금 상태, 정할 것, 확인 지점, 피드백 적는 곳 | 나 |
| `REQUIREMENTS.md` | 무엇을 왜 만드는지, 통과 기준, 범위 밖 | AI |
| `PLAN.md` | 메이저/마이너 분해, 커밋 분기점, 확인 리듬 | AI |
| `review/` | 클린 코드, 구조, 보안 점검표 | AI |
| `AGENTS.md` | 일을 넘겨받을 에이전트가 따를 권한과 금지 사항 | AI |
| `HANDOFF.md` | 지금 어디까지 왔고 다음에 무엇을 할지 | AI |

작은 일이면 `HANDOFF.md` 한 장으로 끝내고, 끝내기 전에 한 번 멈춥니다. 마지막에 바로 실행해도 되는지, 조건부인지, 더 알아봐야 하는지 판정을 알려 줍니다.

이어서 하려면 같은 세션에 "진행해"라고 하거나, 프로젝트 맨 위 폴더에서 새 Codex 세션을 열고 `discovery/날짜_주제/HANDOFF.md 읽고 시작해`라고 붙여 넣으면 됩니다. `HANDOFF.md`가 `AGENTS.md`와 나머지 문서를 읽는 순서를 알려 줍니다. `discovery/` 하위 폴더에서 세션을 열면 Codex 기본 설정에서는 바깥 프로젝트 파일을 고칠 수 없습니다. 실행 중에는 단계마다 멈추고 `사용자_검토.md`의 확인 지점에 결과를 올립니다. 고칠 점은 거기 적은 뒤 "피드백 반영해"라고 하면 됩니다.

### 세션 여러 개로 나눠 돌릴 때: crew

큰 과제를 Codex 세션 3~4개로 나눠 돌립니다. 기본 구성은 작업 하나, 감시하고 알려 주는 노티 하나, 기록 정리 하나입니다.

1. 작업 폴더에서 Codex 세션을 열고 `$crew`를 입력합니다. 이 세션의 역할부터 묻습니다. 처음이면 킥오프를 고릅니다.
2. 킥오프는 과제 README를 읽고, 문제 크기에 맞는 세션 구성을 제안하고, 애매한 부분을 몇 가지 물어본 뒤 `_crew/` 폴더에 요구사항, 계획, 세션별 실행 지시를 씁니다. 끝나면 이 세션은 노티로 바뀝니다.
3. 새 세션을 열어 `_crew/EXECUTION.md`에 적힌 시작 문장을 붙여 넣습니다. 작업 세션을 먼저 열고, 기록 세션은 작업이 좀 진행된 뒤에 엽니다.
4. 그다음부터 지시는 아무 세션에나 말하면 됩니다. 작업 세션이 확인 지점에 닿거나 결정이 필요한 일이 생기면 노티가 macOS 알림을 보내고 `_crew/사용자_검토.md`에 올립니다. 알림을 놓쳐도 그 한 장만 보면 됩니다.

노티는 내 지시와 어긋난 부분만 작업 세션에 수정을 요청합니다. 노티가 스스로 더 낫다고 판단한 것은 나에게 먼저 묻습니다. 작업 세션은 요청이 틀렸다고 보면 이유를 남기고 거절할 수 있고, 그 경우에도 최종 결정은 내가 합니다. 기록 세션은 진행 로그를 `_crew/history.md`로 정리합니다. 경과를 더 자세히 보고 싶을 때만 열면 됩니다.

세션끼리는 `_crew/` 폴더의 파일로만 주고받습니다. 역할 정보는 `AGENTS.md`에 넣지 않습니다. `AGENTS.md`는 그 폴더의 모든 세션이 읽기 때문입니다.

## 보통 쓰는 순서

처음 한 번 `screw-setup`으로 설정하고, 과제마다 `drill-pilot`으로 문제를 이해하고, 필요하면 `drill`로 현업에게 묻고 `gap-assist`로 빈 곳을 메운 뒤, `problem-discovery`로 계획과 인계 문서를 만듭니다. 세션을 나눠 돌릴 만큼 크면 `crew`로 넘어갑니다. 모두 따로 써도 됩니다. 순서와 넘겨주는 방법은 [guides/사용자_주도_작업흐름.md](guides/사용자_주도_작업흐름.md)에 더 자세히 있습니다.

## 파일 정리 지침

[guides/AGENTS.md](guides/AGENTS.md)는 에이전트가 작업 폴더를 어지르지 않게 하는 규칙입니다. 임시 파일 위치, 파일 이름, 원본 보존, 지우기, 커밋 전 확인 같은 내용입니다. 프로젝트 폴더에 복사하거나, 모든 세션에 적용하려면 전역 지침에 덧붙입니다.

```bash
cat screw-problem/guides/AGENTS.md >> ~/.codex/AGENTS.md
```

## 폴더 구조

```
screw-setup/        처음 설정 (역할, 모델, 멀티에이전트, 제약)
drill-pilot/        문제 이해 대화
drill/              현업 인터뷰 (질문 기법, 질문지와 요건정리 양식)
gap-assist/         빠진 곳 점검 (점검 영역 13개)
problem-discovery/  요구사항, 계획, 인계 문서 (유형별 질문, 문서 양식, 검토 점검표)
crew/               멀티 세션 운영 (역할별 지침, 대기와 알림 스크립트)
guides/             파일 정리 지침, 전체 흐름 안내
```

각 스킬의 자세한 규칙은 폴더 안 `SKILL.md`에 있습니다.
